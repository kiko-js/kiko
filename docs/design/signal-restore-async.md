# 设计记录：信号恢复的同步窗口 vs async/Suspend 子树 —— 开放，待讨论

- **日期**: 2026-09-05
- **状态**: 开放（OPEN — 需要讨论方案后再实现；当前已加检测提示，未做架构性修复）
- **决策**: 不做代码层面的「恢复 async 信号」改动。确认这是位置化恢复的固有边界，
  本次只：(a) 在 `stopSignalRestore()` 的数量错位告警里给出 async 提示；(b) 在
  `signal-serialize.ts` 头部如实记录该限制。真正修复需重开设计，见下。

## 背景

kiko 的 SSR 信号恢复是**位置化 + 同步窗口**：

- 服务端在**一个同步渲染栈 + await 整体**后 `serializeSignals()`，快照含 async 子树
  （`<Suspend>` 内 lazy / async 组件）awaited 之后创建的信号，按其文档序 ID 排列。
- 客户端 `hydrateWithState()` 是**单同步栈**：`hydrate()` 返回时（`finally` 里）
  `stopSignalRestore()` 立即关闭恢复窗口。

于是出现不对称：

```
服务端                          客户端
Suspend(async)                  Suspend(async)
  s = createSignal('a')  #0       s = createSignal('a')  #0   ← 窗口内,恢复 ✓
  await …                         await …
  t = createSignal('b')  #1       t = createSignal('b')  #1   ← 窗口已关,不恢复
```

- `t` 拿客户端初始值，服务端快照里的 `#1` 没被消费。
- 若 Suspend 下方还有兄弟信号，它们整体错位消费 `#1..#n`（同 typeof 时静默换值，
  数量错位时报「树不同」——归因误导）。

这是 AGENTS.md「signal creation order must match between server and client」在
async 子树上的直接塌缩：async 子树在两端**创建时机不同**（SSR awaited / client
post-hydration），位置化对齐天然失效。

## 为什么不能简单修

1. **时序不可对齐**：客户端 async 模块在 `hydrate()` 返回后的微任务/宏任务里才跑
   完 await 并 `createSignal`。没有同步点能「等到」它再关窗口，除非把 `hydrate()`
   变异步——破坏现有同步契约（disposer 同步返回、事件立即可用）。
2. **归属不可判定**：恢复是纯位置消费。窗口关闭后创建的信号，无法可靠判断它对应
   服务端快照里哪个迟到 ID——尤其多个 async 子树、乱序 resolve 时。
3. **跨模块状态**：async 子树往往来自独立模块（`lazy`），其信号是模块级、与文档序
   无稳定映射。

## 候选方向（讨论用，未实现）

| 方向                                                                                                                           | 代价                    | 收益               |
| ------------------------------------------------------------------------------------------------------------------------------ | ----------------------- | ------------------ |
| **A. 同步子树内禁 async 信号**：文档/告警要求 async 组件把状态放到 Suspend 外（同步顶层）或模块级，await 后不再 `createSignal` | 约束用户，需可执行检查  | 边界收死，消除盲区 |
| **B. 每异步子树独立小状态包**：async 模块在客户端加载后自行拿「本模块的 SSR 快照」（模块级 key 化恢复，非文档序）              | 新协议 + 序列化格式变更 | 真恢复             |
| **C. 保持现状 + 检测提示**（本次）                                                                                             | 零                      | 至少不误导         |

## 为什么先落 C（不直接实现 A/B）

恢复协议改了要动 envelope 版本号与两端契约，且 B 需要真实消费场景验证 API 形状；
A 的「可执行检查」在编译期做不到（createSignal 在 await 后无法静态识别）。按
`context-scope.md` 的流程约束——讨论优先于实现——先留档，遇 ≥1 个真实 async
状态需求时重开。

## 触发条件

出现真实场景：async 组件在 await 后必须持有**随请求变化**且需水合一致的状态，
且不能上提到同步顶层时，重开讨论 A/B。
